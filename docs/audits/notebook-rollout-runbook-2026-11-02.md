## Prerequisites and all five new indexes

Read-only tooling is available before any writer/index deployment. With an explicit database in a privately provisioned URI file, run:

```powershell
node --import ./server/node_modules/tsx/dist/loader.mjs server/scripts/notebook-preflight.ts "--room=$RoomId" "--uri-file=$PrivateUriFile" --consistency
```

This raw-driver CLI initializes no models, creates no indexes, writes no data and has no apply mode. Without `--consistency` it reports metadata/index checks only. The optional scan is bounded to 5,000 notes and 64 MiB of body data in memory; incomplete scans do not run plans. Complete consistent scans with exact indexes inspect DM and the largest currently valid assigned-player scope, sections All/Journal/Story items, alphabetical/Sessions, offsets 0/360. No assigned player means only DM plans. Require unchanged room scope, complete consistency, zero invalid/unprepared entries, exact indexes and no blocking winning-plan SORT. This does not replace Atlas region/tier/capacity checks, writer drain, backup rehearsal or index-build/write-cost measurements, and it never certifies or enables a room. Treat output as evidence for review, not an automatic production approval.

Use PowerShell from the repo root with Node/server dependencies, MongoDB Database Tools, mongosh and authenticated `vercel.cmd`. Securely provision `MONGO_URI` with an explicit database; never paste credentials into this document. Supply reviewed, project-linked release directories `$ServerFirst` (new server + exact released client) and `$ClientNext` (same server + new client), verified prior deployment URL `$Previous`, `$DatabaseName`, protected dump/restore YAML configs `$DumpConfig`/`$RestoreConfig`, and archive path `$Backup`. Never deploy this mixed working checkout wholesale.
All five indexes below are additive, non-unique, `{locale:'hu'}`; the two original uncollated indexes remain. **Expected build time for each: unknown** until a restored production-sized rehearsal; the timed commands print actual elapsed milliseconds (an already-existing index is not a build benchmark). Production write-latency overhead is likewise unmeasured. Four scalar indexes add one key each per insert/delete; the covering multikey index adds roughly `max(1, distinct characterIds)` keys per document; updates maintain affected keys. Entry writes also add one transactional Room counter update. [MongoDB build behavior](https://www.mongodb.com/docs/manual/core/index-creation/) and [write overhead](https://www.mongodb.com/docs/manual/core/write-performance/).
Prebuild during a monitored low-load window before server rollout; `Notebook.init()`/Mongoose auto-indexing can otherwise start builds even with the reader flag off. Rehearse on an existing consistent production-sized snapshot first; take the fresh pre-backfill backup below regardless. Record per-index times, sizes and write p50/p95 rather than extrapolating fixture read times.

## Server first, client second, backup, then per-room backfill

Vercel Services share one deployment ([Services](https://vercel.com/docs/services)); therefore use two reviewed packages, not an invented backend-only deploy flag. Keep old and new clients supported: default listing stays unchanged; `/navigation`, `navigation=false` (`entries/total/nextOffset`) and `/initial` are additive. [Staging/promotion commands](https://vercel.com/docs/cli/deploy) follow; preserve the deployment URLs returned on stdout and stop on any failed build/smoke test.
```powershell
$ServerOff=(& vercel.cmd deploy --cwd $ServerFirst --prod --skip-domain --env NOTEBOOK_DB_LISTING=off --build-env NOTEBOOK_DB_LISTING=off | Select-Object -Last 1).Trim()
vercel.cmd promote $ServerOff --cwd $ServerFirst
$ClientOff=(& vercel.cmd deploy --cwd $ClientNext --prod --skip-domain --env NOTEBOOK_DB_LISTING=off --build-env NOTEBOOK_DB_LISTING=off | Select-Object -Last 1).Trim()
vercel.cmd promote $ClientOff --cwd $ClientNext
```
Before each promotion, authenticate as DM/player and verify default listing, slim listing, navigation, initial, search/trash, hidden counts and access-loss behavior on its staged URL; after promotion repeat on the public alias. Drain/restrict every older writer/deployment and background/import tool before backfill. Retain the previous and both off-deployments; keep future deployment flags explicitly off until final promotion.
Take a consistent provider snapshot, or externally pause **all** writers through dump completion (the app has no maintenance switch), then run `mongodump --config=$DumpConfig --db=$DatabaseName --archive=$Backup --gzip`; require exit 0 and a restore rehearsal using `mongorestore --config=$RestoreConfig --archive=$Backup --gzip` against an isolated empty target, never live production. Backup must include rooms, notebooks, revisions and their indexes; `server/scripts/backup-local.ts` does not. [Dump documentation](https://www.mongodb.com/docs/database-tools/mongodump/). Resume only the new compatible writers after the consistent backup completes.
```powershell
node --import ./server/node_modules/tsx/dist/loader.mjs server/scripts/backfill-notebook-listing.ts --apply "--room=$RoomId" --batch-size=200 "--checkpoint=$Checkpoint"
node --import ./server/node_modules/tsx/dist/loader.mjs server/scripts/backfill-notebook-listing.ts --check "--room=$RoomId"
mongosh --quiet --nodb --eval 'const d=connect(process.env.MONGO_URI);printjson(d.rooms.findOne({_id:ObjectId(process.env.NOTEBOOK_ROOM)},{notebookListingVersion:1}));'
```
Resume an interrupted/conflicted run with the identical `--apply` command/checkpoint; keep it on durable operator storage. **`--apply` clears that room's marker first, backfills with revision guards, then internally performs the fresh consistency check and guarded marker assignment**; do not manually set it after `--check`. Require exit 0, `complete:true`, no conflicts/invalid rows, certification `ready:true`, separate `--check` with `inconsistent:0`, and marker 1. Incomplete bounded runs can exit 0 without certification. Repair invalid sources separately; use a fresh checkpoint for a fresh full backfill or new derivation version. Repeat for each explicitly selected room; do not omit `--room` accidentally.

## One-room canary, enablement and rollback

Use the explicit room allowlist for a one-room canary. Keep the public alias off while reviewing a deployment-protected, unaliased on-deployment; verify protection before connecting it to production data. New room certification does not bypass the allowlist. Do not unset unrelated rooms' markers to emulate a feature gate.
```powershell
$Canary=(& vercel.cmd deploy --cwd $ClientNext --prod --skip-domain --env NOTEBOOK_DB_LISTING=on --build-env NOTEBOOK_DB_LISTING=on --env "NOTEBOOK_DB_ROOMS=$RoomId" --build-env "NOTEBOOK_DB_ROOMS=$RoomId" | Select-Object -Last 1).Trim()
```
Before enabling, capture matched `before.jsonl` from the off-deployment. For each DM/player, provision host-specific authenticated/protection-approved cookie jars `$OffCookies`/`$OnCookies`; set `$Off=$ClientOff`, `$On=$Canary`, and `$Evidence` to protected storage. Compare unchanged data in a quiet test-room window; repeat for sections, categories, pages, search, trash, tags and character scopes (URL-encode values):
```powershell
foreach($Query in @('?section=all','?section=all&navigation=false','/navigation?section=all','/initial?section=all')){curl.exe -fsS -b $OffCookies "$Off/api/rooms/$RoomId/notebook$Query" -o "$Evidence/off.json";if($LASTEXITCODE){throw 'off read failed'};curl.exe -fsS -b $OnCookies "$On/api/rooms/$RoomId/notebook$Query" -o "$Evidence/on.json";if($LASTEXITCODE){throw 'on read failed'};node -e "const f=require('node:fs'),a=require('node:assert/strict');a.deepStrictEqual(JSON.parse(f.readFileSync(process.argv[1])),JSON.parse(f.readFileSync(process.argv[2])));" "$Evidence/off.json" "$Evidence/on.json";if($LASTEXITCODE){throw 'response mismatch'}}
vercel.cmd promote $Canary --cwd $ClientNext
```
Promote only after exact bodies, freshness/scope headers, cached-navigation revocation (room/assignment/ownership) and hidden-entry behavior pass in the controlled room; otherwise stop. Promotion enables DB reads only for explicitly allowed, currently certified rooms; all others retain JS. Carry both `NOTEBOOK_DB_LISTING` and `NOTEBOOK_DB_ROOMS` explicitly in subsequent releases; deployment environment overrides do not update project-wide defaults. Expand selected room IDs deliberately; use `*` only for a reviewed wider rollout.
Rollback by step: indexes can stay with flag off (they retain storage/write cost); do not drop original indexes. Before client rollout, server rollback is `vercel.cmd rollback $Previous --cwd $ServerFirst`; client/canary/global rollback is `vercel.cmd promote $ServerOff --cwd $ServerFirst` (old client + compatible new server, flag off). If retaining the new client, use `vercel.cmd promote $ClientOff --cwd $ClientNext` to switch the flag off immediately; editing local env alone does nothing. [Rollback constraints](https://vercel.com/docs/cli/rollback) apply; do not roll below the additive server while new clients remain open.
Backfill rollback: Ctrl+C preserves completed metadata/checkpoint; promote an off-deployment, leave derived fields/indexes in place, and resume/check later—source prose, revisions and history are not rewritten. Before permitting any old/out-of-band writer, invalidate the selected room with `mongosh --quiet --nodb --eval 'const d=connect(process.env.MONGO_URI);d.rooms.updateOne({_id:ObjectId(process.env.NOTEBOOK_ROOM)},{$unset:{notebookListingVersion:1}});'` and recertify before re-enabling. Backup failure means stop; genuine source corruption requires a separately approved snapshot restore/cutover after accounting for intervening writes, not an automatic destructive live restore.
