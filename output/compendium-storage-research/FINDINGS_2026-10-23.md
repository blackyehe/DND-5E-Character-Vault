# How 5etools and Dungeon Master's Vault keep browsing fast

Research recorded 23 October 2026. Research only: no application changes, deployment, imports, account changes or restarts.

**Sir, the useful discovery is that these sites avoid doing much of the preparation while you are waiting to browse. They also let your browser reuse data it already has. The size of the library alone does not determine how long it takes to open.**

**1. 5etools: a library of ready-made files.**

Its reference data is available as ordinary JSON files: structured text containing the rules. The live monster directory maps books to separate files, including the Monster Manual, Volo's Guide and the newer Monster Manual. Its website says a basic web server can host a copy; browsing the public rules does not require an account. This avoids having to assemble a different reference library for each visitor. [Live book directory](https://5e.tools/data/bestiary/index.json), [official site FAQ and self-hosting explanation](https://5e.tools/).

Its monster page loads books selected by saved filters, defaults and the entry link. Selecting an additional source can load another book. Once data is loaded, filtering happens inside the browser. This is book-sized loading, rather than necessarily downloading every book or requesting each monster separately. [Source-loading and filtering code](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/js/multisource.js).

There is an important exception: its Items page uses a different, broader item loader, and also filters the loaded items inside the browser. We should not assume every category has the monster page's book-by-book behaviour. The browser still has real work to do when preparing lists. [Items page code](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/js/items.js).

**2. 5etools prepares its search directory before visitors ask to search.**

A build script writes search files in advance. When the site's global search is first used, browser code reads a prepared search file and builds a local search engine from it. Further searches use that engine. Think of downloading a book's index once, then looking up names without asking a librarian on every keystroke. This global search directory is separate from the full monster and item lists. [Search-file generator](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/node/generate-search-index.js), [browser search code](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/js/omnisearch/omnisearch-backing.js).

**3. 5etools can keep downloaded files for later visits.**

Its source includes a service worker: a browser helper that can retain files and return saved copies. File fingerprints identify revisions so the helper can replace changed files. The design distinguishes essential files, optional data/images and external images. This is stronger than simply downloading interface code early. It can reuse the reference data too. This verifies a capability in the published source, not that it was active in a particular visitor's session. [Caching implementation and explanation](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/sw-template.js).

Imported homebrew is also stored through browser storage, and already processed homebrew is reused in memory. Its storage helper supports localStorage and asynchronous storage through localForage, with an IndexedDB availability check. These are different from the downloaded-file cache. [Homebrew storage and reuse](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/js/utils-brew/utils-brew-base.js), [storage helper](https://raw.githubusercontent.com/5etools-mirror-3/5etools-src/main/js/utils.js).

**4. Dungeon Master's Vault: much of imported homebrew lives on your device.**

Its own help page says imported content uses browser local storage. This means accessing an already imported file need not download that file from the account server again. The drawback is that local content can disappear when browser data is removed; another device does not automatically have that same local copy. Account-backed custom items are treated separately. [Official help](https://www.dungeonmastersvault.com/help/).

The public Orcpub community code supports this general picture: it restores imported plugins at startup, persists plugin changes locally and derives reference views from client-side data. Characters, parties and folders have separate server requests. The community edition uses Datomic for its backend; that is not evidence that changing our database to Datomic would fix our delay. [Startup/import events](https://raw.githubusercontent.com/Orcpub/orcpub/develop/src/cljs/orcpub/dnd/e5/events.cljs), [reference views and account requests](https://raw.githubusercontent.com/Orcpub/orcpub/develop/src/cljs/orcpub/dnd/e5/subs.cljs), [community repository](https://github.com/Orcpub/orcpub).

The community repository is not verified to be the exact code currently deployed at dungeonmastersvault.com. The hosted site's help is the stronger evidence for its browser-storage behaviour.

**5. Why our Compendium can still wait despite showing only 25 rows.**

I checked committed source `8010a11`, corresponding to live app `065066d`, rather than the held experimental backend changes.

Our site already has a prepared search/filter catalogue, saved in the database and reused in server memory. It is not starting from nothing on every request. However:

- It checks which version of your library is current before returning the catalogue.
- A missing catalogue can cause the request to read and process the imported library, then build a replacement while you wait.
- The saved catalogue expires after seven days. Its version also depends on packs, standalone items and personal Compendium edits, so an unrelated category edit can prevent reuse of a previous catalogue.
- Full entry reading already has a separate, more targeted path; list preparation and opening one entry are different jobs.

Showing 25 rows reduces the response and drawing work after preparation. It does not remove the work needed to prepare a missing catalogue. These are verified code paths, not proof that any one of them caused every reported ten-second delay.

Local evidence: `server/lib/compendium-browse.ts` (`browseRevision`, `loadIndex`, `buildIndex`), `server/lib/workshop-library.ts` (`workshopLibrary`, `buildLibrary`) and `server/models/CompendiumBrowseIndex.ts`, all read with `git show 8010a11:<path>` from the combined release worktree.

**6. What is worth borrowing.**

My recommendation is to investigate keeping a ready-to-read catalogue as durable derived data, updated when its actual source changes. Keep descriptions and artwork separate from the small list used to search. This builds on our existing catalogue rather than replacing the site or changing database brands.

Where preparation runs matters. Doing it during import can lengthen imports; doing it in a background job needs reliable completion and failure handling. We must not advertise either as free, or show old rules as though they were current. First measure how often we rebuild and which part consumes the time.

Browser copies of unchanged catalogue chunks could then improve repeat visits. They would remain disposable copies, with the server retaining the originals and checking the correct account and version. A fresh browser still needs a first download, and any local reuse must handle sign-out, account switching and updates correctly.

This is a more promising direction for a slow data request than warming interface files alone. It does not yet justify an implementation or a promised load time. We should retain cross-device access and private-pack permissions rather than copying DMV's local-only homebrew model wholesale.

**7. What this research does not establish.**

There is no verified "zero loading time" benchmark here. First visits still download files and process data; repeat visits may reuse much of it. We did not obtain a controlled fresh-browser comparison of either external site. T3 preview navigation and repeated snapshots timed out (`Preview automation navigate timed out after 15000ms`; `Preview automation snapshot timed out after 15000ms`), so those attempts are not website performance measurements. Findings rely on public first-party pages, published implementation and our committed source.

No evidence here calls for downloading our entire roughly 90 MB aggregate into every browser. No changes to the paused prefetch/configuration experiment or to production are included in this research.
